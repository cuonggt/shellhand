**Accepting a new host key could bring the question straight back.** The
first time you connect to a machine, ssh asks whether to trust its key. On a
server that logs in quietly — no "last login" line, no message of the day —
saying yes was not enough: the question came back at once, as though it had
never been answered. Saying yes a second time then typed `yes` into the shell
you had just logged into, which runs the `yes` command and fills the terminal
with `y` until you press Control-C; saying no typed `no` into it instead. A
question you have answered now stays answered.

**A terminal no longer carries the app's own connections with it.** When a
terminal session started, the `ssh` behind it was handed copies of whatever
the app had open at that moment — the connections behind an open SFTP window,
and the watch the app keeps on your host list — and held them for as long as
it ran. Nothing ever used them, but nothing should have been handed them
either. They stay with the app now.

Nothing else here is visible from the outside. The suite went from 421 checks
to 448, and for the first time it holds the app against the real thing rather
than a stand-in: SFTP against OpenSSH's own server, and `ssh` itself —
connecting, keys, jump hosts, and a terminal answering a real host-key
question — against a server started for the length of each test. The first
fix above was found that way, on the first run of a test written to look.
